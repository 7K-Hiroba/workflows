# Consumer guide

## v2.0.0 breaking migration

Workflows v2.0.0 requires every adopting consumer to migrate to `inari.hiroba.app.v2` and explicitly declare `archetype: stack|non-stack`. A stack must also declare complete install plus same-cluster upgrade lifecycle coverage and pass its immutable lifecycle caller; a non-stack must not acquire that lane. Consumers that are not ready to make those changes must retain their immutable v1.1.0 workflow pin (`b26b53f5ba58a27d1973fec6dfa6469d0b93ba62`) until migration is complete. Do not treat v2.0.0 as a SHA-only or version-comment-only update.

1. Generate the app through the CLI scaffold after the workflow release is approved.
2. Migrate to app config v2 with explicit `archetype: stack|non-stack`. Every stack declares complete `tests/stack` install+upgrade coverage and its immutable caller; non-stack sources never emit them. Follow `docs/stack-testing.md`. Keep `.hiroba.yaml`, extension/package/template manifests, values schemas, canonical observability, generated outputs, and optional `tests/smoke/` synchronized. Chartless observability omits `observability.chart`; runtime smoke declares an explicit `helm` or `manifests` adapter and its allowed `executableProfiles`.
3. Use thin callers from `scaffold/.github/workflows/*.template`. The renderer replaces `__WORKFLOWS_V1_SHA__` with the full approved commit SHA and preserves the version comment. Placeholders, `@v1`, `@main`, and short SHAs fail policy.
4. Use only explicit App credentials for release-please/finalization; never `secrets: inherit`. PR lanes require contents-read only.

Declare `releaseComponents` only for package, template, chart, or standalone-smoke components that need a non-legacy signed Release identity, and remove stale entries when components are removed. Backend/UI identities remain fixed as `extension-vVERSION` and `ui-vVERSION`. Artifact-bound smoke must not have its own entry because it inherits the target. Backend-only repositories require backend compatibility evidence; UI-only repositories require browser evidence; repositories with both retain the combined lanes. The compatibility matrix is valid for any of these selections. Chart repair discovers the configured `releaseComponents` identity, uses legacy `NAME-vVERSION` when no mapping exists, and requires that exact annotated tag.

Generated release-please packages make every identity visible: fixed `extension`/`ui`, an explicit `releaseComponents` value, a standalone-smoke identity, or the discovered legacy Chart.yaml name/package/template directory. The global `include-v-in-tag` remains `true`; each componented package sets it to `false`, so the existing `-v` separator emits exactly one `v` and componentless bare versions are never canonical. Legacy names retain their spelling but must be Git/release-please-safe, must not contain `--components--`, and must be globally unique independent of kind or version before any generated file is written. Resolve collisions deliberately with kind-qualified explicit identities such as `chart-NAME` and `package-NAME`; the generator never silently renames a component.
5. Require the stable `library CI / result` and `scaffold CI / result` checks after verifying the exact names on a completed PR run. Keep matrix summary names stable.
6. Let Renovate propose workflow/action/chart/SDK updates; trusted workflow updates are manually reviewed.

## Backend and UI release versions

`components.extension.version` and `components.ui.version` in `.hiroba.yaml` are the canonical current-version inputs. The release-please manifest is generated from them, and backend and UI versions remain independent: a backend release must not select the UI version, and a UI release must not select the backend version. Never add a shared version, `release-as`, or linked-versions override to force them to match.

Opt runtime source declarations into synchronization by putting `x-release-please-version` on the exact version line, for example `Version = "0.1.0" // x-release-please-version` in Go or `version: '0.1.0', // x-release-please-version` in TS/TSX. The generator discovers marked Go, TypeScript, and TSX files below the configured component roots; legacy unmarked files remain unmanaged. It preserves all source formatting outside the version token and preflights every declaration before writing. Missing, malformed, ambiguous, or previously managed declarations that disappear fail closed without partial writes.

Run `scripts/sync-release-please-config.py --root <consumer>` after changing canonical metadata instead of hand-editing generated declarations. CI runs the same generator with `--check`, which reports drift without writing. The generated `extra-files` let release-please update marked source files, the repository-root `extension.yaml` marker, and the exact `.hiroba.yaml` component nodes on Release PRs while retaining the existing native extension, package, lockfile, chart, and changelog updates. Release-please alone selects next versions. Its targeted YAML updater may normalize `.hiroba.yaml` presentation; unrelated YAML content must remain semantically unchanged. The root generic updater changes only the marked extension version token for LF input; CRLF normalization is not claimed to preserve bytes and must be reviewed explicitly.

A non-stack-covered chart may independently opt into the strict same-release install→upgrade declaration in `docs/chart-testing.md`. This does not require or permit stack reclassification, runtime-smoke substitution, an extra kind cluster, or an install-only consumer migration. Existing charts remain install-only until they deliberately add reviewed previous/current packages and targeted assertions.

The scaffold is a contract fixture, not a trusted app. Do not register its CI artifacts as a source. Real deployment and environment verification are separate tasks.
